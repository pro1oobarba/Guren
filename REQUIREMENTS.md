# AI Kernel — Техническое задание (ТЗ)

## 1. Общее описание

**AI Kernel** — модульное Node.js приложение, которое служит универсальной прослойкой между проектами Вовы (AI Dungeon Master, Telegram боты, анализ документов) и несколькими бесплатными AI-провайдерами.

**Главная идея:** один вызов `AI.generate({ task, prompt })` — и ядро автоматически выбирает лучшую доступную модель, делает запрос, а если модель не ответила — молча переключается на следующую. Проекты не должны знать, какой именно провайдер ответил.

---

## 2. Требования к стеку

- **Node.js:** версия 22 и выше
- **Встроенный `fetch`:** никакого `node-fetch`, только нативный (доступен в Node 18+)
- **Загрузка переменных окружения:** `node --env-file=.env index.js`, без пакета `dotenv`
- **Никаких внешних npm-пакетов:** весь код для MVP — только встроенные модули Node.js
- **ESM модули:** `"type": "module"` в `package.json`, импорты через `import`

---

## 3. Архитектура на высоком уровне

### 3.1 Паттерны

- **Strategy (Стратегия):** каждый провайдер (Groq, OpenRouter, Cloudflare) — отдельный класс, наследующий `BaseProvider`
- **Facade (Фасад):** класс `AIKernel` скрывает всю сложность и предоставляет простой API (`AI.generate()`, `AI.code()`, и т.д.)
- **Registry (Реестр):** `ModelRegistry` хранит стейт всех моделей (живая ли, задержка, ошибка)
- **Router (Маршрутизатор):** `Router` выбирает модель под задачу и реализует авто-fallback

### 3.2 Разделение ответственности

Каждый модуль делает одно:
- **Providers** (`BaseProvider`, `groq.js`, `openrouter.js`, `cloudflare.js`) — общение с провайдерами
- **Registry** — хранилище стейта моделей (ничего не знает о провайдерах)
- **Router** — выбор модели и fallback логика
- **HealthChecker** — пинг всех моделей, запись результатов в реестр
- **MemoryManager** — история сообщений по sessionId, отделена от провайдеров (stateless)
- **Kernel** — главный фасад, объединяет всё вместе

## 4. Функциональные требования

### 4.1 Поддержка провайдеров

На старте MVP нужны:

| Провайдер | Статус | Бесплатный лимит | Эндпоинт |
|-----------|--------|-----------------|----------|
| **Groq** | ✅ Работает | ~1000 запросов/день | `https://api.groq.com/openai/v1` |
| **OpenRouter** | ✅ Работает | 50–1000 запросов/день (фильтруем только бесплатные модели) | `https://openrouter.ai/api/v1` |
| **Cloudflare Workers AI** | ✅ Работает | 10 000 "нейронов"/день | `https://api.cloudflare.com/client/v4/accounts/{id}/ai` |
| **GitHub Models** | ❌ Закрыт (30.07.2026) | N/A | N/A |

**GitHub Models** был в исходном ТЗ, но GitHub закрыл сервис 30 июля 2026 году. Его реализация оставлена как заглушка-шаблон (`providers/github.js`), пригодится как пример для добавления похожих сервисов.

### 4.2 Получение списка моделей

Каждый провайдер должен реализовать `listModels()`, который возвращает:
```js
[
  { id: "model-name", provider: "groq", contextWindow: 8192 },
  { id: "other-model", provider: "openrouter", contextWindow: 32000 },
  ...
]
```

**Особенность OpenRouter:** список содержит сотни моделей. На health-check пропускаем платные (оставляем только где `pricing.prompt === 0` и `pricing.completion === 0` или `id.endsWith(':free')`), чтобы не улететь в rate limit.

### 4.3 Health-Check / Benchmark

При старте ядра (`AI.init()`) система:
1. Пингует каждую модель коротким запросом ("ping")
2. Измеряет `latency`
3. Помечает модель как `alive: true` или `alive: false`
4. Сохраняет результаты в `ModelRegistry`
5. Сохраняет отчёт в `health-report.json` (опционально)

**Консольный вывод должен быть красивый** — цветной текст, timestamps, иконки (✓, ✗, ⚠).

### 4.4 Умный роутинг

`Router.rank(task)` ранжирует живые модели по:
1. Совпадению ключевых слов в названии модели (для задачи)
2. Низкой задержке (latency)

**Задачи:**
- `'code'` → ищет модели с ключевыми словами: coder, code, deepseek, qwen, devstral
- `'roleplay'` → dolphin, hermes, nous, mythomax, chat
- `'analysis'` → 70b, 72b, 405b, large, instruct
- `'general'` → по умолчанию

Это **мягкая эвристика**, не научный рейтинг. Для бесплатных моделей нет объективного бенчмарка в реальном времени.

### 4.5 Авто-Fallback

Когда `Router.execute()` пробует модели по рангу:
1. Берёт первую ⟹ пробует её `chat()`
2. Если `OK` → возвращает результат, сохраняет в истории
3. Если ошибка → помечает модель как `alive: false`, логирует ошибку, идёт к следующей
4. Если все модели упали → выбросить ошибку с последней ошибкой

**Это должно быть прозрачно** — клиент видит только финальный результат или исключение, не все попытки fallback.

### 4.6 Единый интерфейс

`AIKernel` экспортирует:
```js
AI.generate({ task, prompt, sessionId, systemPrompt })  // базовый генератор
AI.code({ prompt, sessionId, ... })                      // task='code'
AI.roleplay({ prompt, sessionId, ... })                  // task='roleplay'
AI.analyze({ prompt, sessionId, ... })                   // task='analysis'
AI.init({ saveReport, reportPath })                       // инициализация + health-check
```

Возвращаемое значение:
```js
{
  text: "...",              // текст ответа от модели
  provider: "groq",         // какой провайдер ответил
  modelId: "llama-3.3-70b"  // какая именно модель
}
```

### 4.7 Контекст / История сообщений

`MemoryManager` хранит историю **отдельно** от логики провайдеров:
- Ключ: `sessionId`
- Значение: массив `[{ role: 'user' | 'assistant', content: '...' }]`
- Stateless: роутер и провайдеры просто получают готовый массив `messages`, ничего не знают про память

При `generate()`:
1. Берём историю сессии из памяти
2. Добавляем `systemPrompt` (если есть) в начало
3. Добавляем текущий `prompt` как user-сообщение
4. Отправляем провайдеру
5. Получаем ответ
6. Сохраняем user + assistant в историю (для следующего вызова)

## 5. Нефункциональные требования

### 5.1 Production-Ready на уровне MVP

- Все async операции обёрнуты в try-catch
- Понятные сообщения об ошибках (что случилось и как это исправить)
- Логирование в консоль с цветом и временем
- Graceful shutdown (нет зависающих промисов)

### 5.2 Отсутствие зависимостей

Никаких `npm install` для MVP. Только встроенные Node.js модули:
- `node:fs/promises` (запись health-report.json)
- встроенный `fetch`

### 5.3 Переменные окружения (.env)

Загружаются через `node --env-file=.env`, доступны в `process.env`:
- `GROQ_API_KEY`
- `OPENROUTER_API_KEY`
- `CLOUDFLARE_ACCOUNT_ID` + `CLOUDFLARE_API_TOKEN`
- `APP_SITE_URL` (опционально)
- `APP_NAME` (опционально)

## 6. Ограничения (осознанные, не баги)

1. **Память в памяти процесса:** при перезапуске история теряется. Для persistence нужна файловая система или БД.
2. **Ранжирование по ключевым словам:** для бесплатных моделей нет объективного рейтинга, эвристика работает примерно.
3. **OpenRouter: недели меняется free-лайнап:** список запрашивается заново при каждом `init()`, не хардкодится.
4. **GitHub Models:** закрыт, провайдер для него — заглушка.
5. **Нет логирования в файл:** логи только в консоль (можно добавить позже через `> output.log`).

---

## 7. Как добавить нового провайдера

1. Создай `providers/newprovider.js`
2. Унаследуй от `BaseProvider`
3. Реализуй `listModels()` и `chat()`
4. Подключи в `kernel.js` в объект `this.providers`
5. Добавь переменные окружения в `.env.example`

Никаких других файлов менять не нужно. `Router` и `HealthChecker` подхватят новый провайдер автоматически.

## 8. Обработка ошибок

### Провайдер недоступен (нет ключа)

```
[WARN] groq: пропущен (нет ключей в .env)
```

### Список моделей не получен

```
[ERROR] openrouter: не удалось получить список моделей — HTTP 429
```

### Модель не ответила / мертва

```
[WARN] ✗ groq/llama-3.3-70b — тайм-аут, пробуем следующую модель
```

### Все модели недоступны

```
[ERROR] Все подходящие модели недоступны. Последняя ошибка: rate limit
```

✅ `npm run start` запускается без ошибок

✅ Тестовый запрос через `AI.generate()` возвращает текст

✅ История сообщений сохраняется по sessionId

✅ Цветной логирование в консоль

✅ Никаких npm-пакетов, только встроенные модули
